Q·01 13.5 Once the personas walk a live browser and say DONE or NOT, who on the team actually turns that verdict into a design decision, and can anyone decline what the panel asks for? DesignerNew to agents

In my process, whoever owns the product is the one who decides whether a NOT is a simple fix to make inline or something pervasive enough to re-run the panel. Disagreements get settled by naming the design principle behind each side, never by majority vote or by deferring to my own ask — and refusals are logged explicitly, with the reasoning attached, rather than complied with silently. So yes, the panel's verdict can be declined; the record just requires writing down why when that happens.

Q·03 12 Beyond the gate and flag, what stops an unattended agent run from merging broken code or overspending before you check on it? EngineerPM

Beyond the bar and the flag, each run got hard caps set before it started — a cap on tool calls, on wall-clock time, and on spend, written into the lane brief rather than buried in a config file. Production also had guard rails that refuse unsafe configuration at boot, and the gate itself was judged offline against frozen, recorded data rather than a live session, so nothing merges on a live judgment call. Each run also got a named end time instead of an open-ended 'overnight.' It wasn't airtight — before I added a watchdog, an idle tab used up a full day's API allowance overnight.

Q·14 4 Once a gate passes, does the lane merge on its own, or do you still review the diff before it lands? New to agents

No, a passed gate doesn't merge itself. The checklist calls for a stronger model to review each lane first, naming what it actually checked — re-running the gate's command, spot-checking specific claims, diffing against the contract, not just "looks good." Only after that review does the merge happen, with `merge --no-ff` and a commit body stating what was learned. The unattended-run diagram shows the same order: a cleared gate unlocks the next lane, but only a cleared and reviewed gate reaches me for the production flip or merge decision. So review comes before landing, not after.

Q·20 4 What does 'one tier up' actually mean in terms of which models you use for building versus reviewing? New to agents

It means the model reviewing a lane's output has to be a stronger tier than the model that built it, never a peer — the ordering runs haiku to sonnet to opus to my strongest model. A sonnet-tier build lane gets an opus-tier reviewer, for example. And the review can't just say 'looks good' — it has to state plainly what it checked, like a count, a spot-check with exact lines, or a re-run of the gate's command. My strongest model is the one writing the briefs and judging results, while I make the final calls.
