Q·01 5 Concretely, what is a gate checking — a script's exit code, a numeric threshold, or a human reading a report? New to agents

It depends which gate. For the test suites (pregrade, scout, card-refresh, sources), a gate is a script's exit code plus a positive count — the write-ups insist a fail line without an exit code isn't a gate, and totals have to be an actual summed count, not an eyeballed pass. For UI/labeling work, the gate is different: a panel of personas and critics walks the built screens and returns a verdict of DONE or NOT DONE, with blocking items. And mechanically, a gate has to be chained with `&&`, not `;`, or a failing check won't stop the next step.

Q·04 5 Who actually turns a persona's NOT verdict into a design change, and can that person decline what the persona is asking for? Designer

The record says designers — whether human, agent, or persona — are the ones who turn a NOT verdict into the change, and I ruled they must never just implement the literal ask; they translate it into the underlying job first. For a simple, measurable fix, whoever owns the product decides it's small enough to fix inline without re-running the panel. And yes, they can decline: the plan tracked each ask as accepted, reshaped, or declined with a reason, and refusals were logged explicitly rather than silently complied with, since a documented refusal outlives silent compliance.

Q·11 5 What's actually in the unattended.md file — how do you set the end time, the caps, and get a morning report without building your own platform? New to agents

There's no platform behind it — it's just conventions written into a file. The end time is one line in the lane brief: run continuously until a named hour, then stop or pause, not "run overnight." Caps are three numbers set before the run starts, also written into the brief so they're visible: a cap on tool calls, one on wall-clock time, one on spend. The morning report is a single file, not a pile of logs — each lane writes its own short report into it, or a coordinator assembles them, so I read one file in the morning instead of chasing logs.

Q·18 4 What actually stops an unattended overnight agent from merging a change that passes its gate but is wrong in a way the gate didn't anticipate? Engineer

The record's answer is the flag, not the gate. A gate only checks the result against a bar decided in advance, so it can pass something wrong in a way that bar didn't cover. What stops that from reaching users is that new behavior ships behind a flag that defaults off in production even after merging — a lane can flip its own dev flag, but only I flip the production flag, explicitly, the next morning, never automatically when a lane finishes. So a bad merge sits inert until I look at it. Beyond that, the record doesn't show additional unanticipated-error catches.
